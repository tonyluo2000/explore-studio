# Phase E Online Foundation v0.1

> **Status:** Implemented foundation contract. Owner authority is recorded in
> [GitHub issue #31](https://github.com/tonyluo2000/explore-studio/issues/31).
> This contract deliberately contains no HTTP endpoint or workflow service.

## Purpose

The Phase E foundation supplies the trusted data and authorization primitives
that later publication, approval, registry, and configuration services must use.
It does not make those services exist.

The lifecycle remains explicit:

```text
commit ≠ export ≠ publish ≠ approve ≠ release
```

Local development, validation, tests, loading, and deterministic export do not
import `explore.online`, open its database, or require authentication.

## Implemented boundary

`explore.online` defines:

- immutable internal actor IDs bound once to a configured federated OIDC
  issuer and its opaque provider subject;
- institution-authority cohorts with one approved role per actor and cohort;
- globally unique package namespaces, explicit owners, and same-cohort submit
  grants;
- immutable `(package_id, semantic_version, raw_zip_sha256)` package-version
  identities;
- the owner-approved deny-by-default authorization matrix;
- append-only canonical audit events without mutable profile fields; and
- immutable completed-operation idempotency records.

The foundation module alone does **not** implement OIDC protocol exchange,
sessions, account recovery, submission/upload, terms acknowledgment, review or
approval transitions, retention jobs, or Class-World configuration mutations.
Bounded submission, review, registry, pinning, and authenticated control-plane
services are defined by their separate additive Phase E contracts.

## Identity and privacy

An `Actor.actor_id` is a canonical UUID generated by the trusted service. It is
not an email address, display name, repository owner, or provider subject. The
`(issuer, subject)` pair is unique and immutably maps to exactly one actor.
Only explicitly configured HTTPS issuers are accepted by persistence.

The foundation records no email, display name, date of birth, guardian data, or
password. A cohort records its institution-managed account authority. Audit
details reject common mutable identity/profile keys; trusted services should
refer to actors only by internal ID.

Authentication code added later must use federated OIDC with authorization code
and PKCE. It must derive assurance from verified provider claims. Teacher and
course-admin authorization requires AAL2/MFA; client assertions never set the
assurance level.

## Membership and namespace ownership

Memberships are scoped by `(cohort_id, actor_id)` and admit only `student`,
`teacher`, or `course-admin`. There is exactly one current role in a cohort.
Trusted operator provisioning creates a cohort and its initial active
course-admin atomically; there is no separate self-enrollment path. Every later
assignment must name an active course-admin grantor.

A package ID is global. Its namespace has one owning cohort and one owner who
must be a member of that cohort. Explicit `submit` grants can target only a
member of the same cohort and can be issued only by an active course-admin.
Namespace transfer is supplied by the additive
[Phase E Authenticated Control Plane v0.1](phase-e-control-plane-v0.1.md). It
authorizes the current course-admin at AAL2, compares the expected revision,
increments the revision once, and appends audit and idempotency evidence in the
same transaction.

## Authorization

`authorize()` is the single policy entry point for the approved matrix:

| Principal | submit | review | approve | revoke | registry-read | pin | configure |
|---|---|---|---|---|---|---|---|
| student | owned/explicit namespace | no | no | no | own or cohort-approved | no | no |
| teacher | explicit namespace only | assigned cohort | assigned cohort, never self | no | assigned cohort | exact approved, not revoked | no |
| course-admin | explicit namespace only | administered cohort | administered cohort, never self | administered cohort | administered cohort | exact approved, not revoked | administered cohort |
| service principal | no | no | no | no | exact approved workload grant only | no | no |

The policy requires a current membership for every human operation. Privileged
roles additionally require AAL2. Revoked versions remain readable for
authorized historical use but cannot receive a new pin.

`HumanPrincipal` and `AuthorizationResource` are trusted server-side snapshots.
A future handler must load actor, current membership, namespace owner/grants,
cohort, exact package identity, approval, and revocation state from persistence
after authentication. It must not copy those attributes from a request. Direct
object and list/search paths must call the same policy. Object identifiers are
not authorization secrets, and external error mapping must not reveal whether a
forbidden object exists.

## Persistence and concurrency

`SQLiteFoundationStore` is a dependency-free reference implementation of the
foundation persistence semantics. It is not an HTTP service or a deployment
choice. A different production database must preserve all constraints and
transaction boundaries before it is considered conforming.

The schema enforces:

- unique issuer/subject and actor bindings;
- approved role values and one membership per actor/cohort;
- a global package-ID primary key and same-cohort ownership/grants;
- one digest and provenance record for each package ID/version;
- update/delete rejection for federated bindings and package-version identity;
- update/delete rejection for completed idempotency records;
- update/delete rejection for audit events;
- unique audit operation keys; and
- next-revision checks for membership and namespace updates.

Writes use `BEGIN IMMEDIATE` so competing writers serialize before inspecting
then inserting identity records. `transaction()` groups one future mutation,
its audit event, and its completed idempotency result. Reuse of an idempotency
key with different request bytes fails closed; an identical retry returns the
original result reference.

Each cohort has an explicit close time and every audit event has an immutable
retention deadline. The approved default retains artifact bytes through cohort
close plus one year and authorization/approval audit through cohort close plus
two years. This foundation stores no artifact bytes; a later artifact store must
enforce the first deadline. Audit rows are append-only to application code.
Retention must not become an ordinary mutation endpoint: a future partition or
archival implementation may purge expired data only through a separately
authorized, audited process with least-privilege administrative access.

## Package identity

The online identity uses the existing package ID and Semantic Versioning rules.
`raw_zip_sha256` is the SHA-256 of the deterministic Explorer Package ZIP bytes.
Recording it does not change export bytes or semantics. A package ID/version may
be replayed only when the digest, cohort, and creating actor match; it cannot be
rebound to different bytes.

## Explicit exclusions

This foundation does not add or change:

- submission or upload endpoints;
- publication terms or acknowledgment UI;
- approval, rejection, or revocation workflow state;
- an approved-registry projection;
- Class-World pin/configuration behavior;
- package signing or attestations;
- deployment or publication infrastructure;
- moderation; or
- student-code execution or isolation.
