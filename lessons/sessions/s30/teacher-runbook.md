# S30 — World Premiere

**Role:** Project-primary production lesson

**World reuse:** M16 `present-your-capstone-expedition`, which reuses the
existing M01 `ALL_OBJECTS_VISITED` completion behavior; the capstone also
demonstrates its existing M14 and M15 mechanics.

**Learning objective:** Students can present a substantial reviewed expedition,
explain its modular Python and algorithm choices, show final validation and
deterministic-export evidence, and recover from one likely demo failure.

**Prerequisite:** The student's S29 review-complete capstone, persistent project
record, green regression evidence, valid package, and explainable accepted AI
assistance.

## Before class

- Keep the student's real S29 reviewed capstone primary. The Skyglass materials
  are a comparison and access fallback, never a substitute for original work.
- Confirm the final evidence path is local and supported for descriptor-confined
  export. Prepare two fresh output directories; never overwrite old evidence.
- Confirm Mission 16 is already available and uses `ALL_OBJECTS_VISITED`.
- Do not add or request runtime, schema, Mission, Trail, publication, approval,
  signing, deployment, authentication, or Phase E work.
- Review the student's access path and keep printed receipts/text walkthrough or
  teacher-operated Trail available.

## Gate 1 — reviewed state and predictions

The student names the reviewed S29 commit and distinguishes deliberate deferred
work from accidental unfinished work. Before commands run, require predictions
for focused/full tests, ordered export members, repeat-export equality, and the
visitor's object observations. No feature work starts during premiere rehearsal.

## Gate 2 — final technical receipt

Require evidence for:

- normal, boundary, invalid, and regression tests;
- the focused learner suite and appropriate complete project suite;
- Explorer Package validation with zero issues;
- successful local Trail planning;
- two fresh deterministic exports with identical member metadata, archive byte
  count, SHA-256, and raw bytes; and
- the stable ordered member list.

`premiere_evidence.py` is a small support harness the student must explain. It
validates before planning, selects existing Mission 16, exports into distinct
fresh directories, and compares both metadata and raw bytes. If a stage fails,
the harness raises one narrow error and does not claim a complete receipt.

Export remains local. Repeat explicitly:

```text
commit ≠ export ≠ publish ≠ approve ≠ release
```

No login, upload, registry, signing, deployment, or release action belongs in
this lesson.

## Technical explanation rubric

The student traces nested source data through named module responsibilities to
deterministic package documents. They explain at least two meaningful search,
filter, count, aggregate, or sort operations, including input/output shapes and
why the chosen operation fits. For one algorithm, require intermediate state,
stable ordering, boundary behavior, and its protecting test.

Ask for one narrow defensive failure path and why it fails closed. Ask why the
runtime consumes validated declarative YAML rather than local student Python.
The student also tells one evidence-linked debugging or refactoring story from
S25–S29: prediction, observed evidence, change, result, and lesson.

## Demonstration recovery

The student scripts one likely failure before the premiere. A complete recovery
has six parts: name the symptom, stop, inspect one relevant diagnostic or
receipt, make one bounded correction, rerun the exact failed check, and resume
at a named point. Do not reward frantic unrelated edits or concealed red output.

If live recovery would consume the demonstration, preserve the failure, use the
last clean receipt, have the student explain the predicted correction, and move
to the text or teacher-operated Trail access path.

## M16 tour and assessment boundary

Use Mission 16 `present-your-capstone-expedition`. It adds no behavior: it reuses
the existing all-objects-visited rule. The student guides the visitor to every
world object, describes each payoff, identifies the existing M14 named shared
toggle style, and demonstrates the existing M15 correct order and
wrong-member/reset path.

Trail `Complete` certifies only the guided object tour. Separately assess Python
quality, modularity, two algorithms, tests, validation, deterministic export,
technical explanation, recovery, originality, and AI disclosure. Never present
Trail completion as mastery, approval, publication, or release readiness.

## Questions and AI boundary

Questions require the student to point to code, data, tests, or evidence. They
must explain every accepted line and disclose accepted AI help across the
capstone.

In S30, AI may ask at most **TWO rehearsal questions only**, after the student's
own script and recovery prediction. The student supplies the answers. AI may
not answer for the student, rewrite code, generate the presentation or package,
repair failures, invent evidence, assess mastery, or add features.

## Git close, support, and cut line

Use status → diff → staged diff → one descriptive final reviewed commit. An
optional tag stays local and points to that commit; publishing and deployment
remain outside the course.

For access, accept printed receipts, text diff/output, object names and
coordinates, narrated algorithm state, and teacher-operated Trail. Preserve
student explanation and evidence; do not silently perform the demo or recovery.

By 0:41 protect green tests, valid package, matching exports, one algorithm
walkthrough, one recovery rehearsal, every-object M16 tour, M14/M15 observations,
and the explicit completion boundary. Defer cosmetic polish, optional tagging,
extra questions, and all new features. This lesson adds no S31 materials or
engine/schema/Student API/Trail/Mission/runtime behavior, publication,
deployment, authentication, or Phase E work.
